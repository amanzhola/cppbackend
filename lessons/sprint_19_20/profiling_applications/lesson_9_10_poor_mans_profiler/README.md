# 🧰 Lesson 9/10 — Poor Man's Profiler

## 📌 Описание

В этом упражнении изучается подход **Poor Man's Profiler** — «профайлер бедного человека».

Идея подхода простая:

```text
запущенная программа
↓
подключение GDB
↓
остановка процесса на короткое время
↓
снятие стека вызовов
↓
detach
↓
повторение несколько раз
```

Если одна и та же функция часто попадает в `backtrace`, значит программа проводит в ней много времени.

---

## 🧠 Главная идея

Вместо специальных профилировщиков можно использовать обычный отладчик:

```text
GDB снимает стек вызовов работающего процесса.
```

Это полезно, когда:

* нельзя пересобрать программу с `-pg`;
* `perf` недоступен или неудобен;
* нужно быстро понять, где зависает или долго работает приложение;
* важно видеть wall clock time, а не только CPU time.

---

## ⚠️ Важно про YC / Linux

Урок лучше выполнять на YC или полноценной Linux-машине.

На сервере может быть включена защита:

```text
/proc/sys/kernel/yama/ptrace_scope
```

Из-за неё обычная команда:

```bash
gdb -p PID
```

может завершиться ошибкой:

```text
ptrace: Operation not permitted
```

В таком случае нужно подключаться так:

```bash
sudo gdb -p PID
```

## 🚀 Самый короткий рабочий сценарий

```bash
cd ~/cppbackend/lessons/sprint_19_20/profiling_applications/lesson_9_10_poor_mans_profiler

g++ -O2 -g main.cpp -o app

./app &
APP_PID=$!

echo "PID=$APP_PID"

ps -p $APP_PID

sudo gdb -p $APP_PID
```

Внутри GDB:

```gdb
bt
detach
quit
```

После выхода из GDB:

```bash
kill $APP_PID
```

## 🧯 Частые ошибки

### 1. Файла `app` нет

Ошибка возникает, если программа ещё не собрана.

Решение:

```bash
g++ -O2 -g main.cpp -o app
```

Проверить:

```bash
ls -la app
```

---

### 2. `ptrace: Operation not permitted`

Причина — Linux-защита `ptrace_scope`.

Решение:

```bash
sudo gdb -p PID
```

---

### 3. Программа завершилась до подключения GDB

В этом уроке программа должна работать долго или бесконечно.

Проверить процесс:

```bash
ps -p PID
```

Если процесса нет — запустить заново:

```bash
./app &
APP_PID=$!
```

---

## 🧠 Почему это работает

Если функция работает дольше остальных, вероятность поймать её в стеке выше.

Например:

```text
FastFunction работает 10 ms
SlowFunction работает 100 ms
```

Тогда `SlowFunction` будет попадаться в `bt` примерно чаще.

Так формируется простая статистика без полноценного профилировщика.

## 🆚 Сравнение подходов

| Подход              | Как работает                               | Плюсы                          | Минусы                                      |
| ------------------- | ------------------------------------------ | ------------------------------ | ------------------------------------------- |
| `LOG_DURATION`      | Ручные замеры в коде                       | Просто и понятно               | Нужно менять код                            |
| `gprof`             | Инструментирование через `-pg`             | Даёт отчёт по функциям         | Нужно пересобирать программу                |
| `perf`              | Статистическое профилирование              | Мощный Linux-инструмент        | Может быть недоступен в WSL                 |
| Poor Man's Profiler | GDB подключается к процессу и снимает стек | Можно использовать почти везде | Останавливает процесс на время снятия стека |


Главная идея:

```text
Если многократно снимать стек работающего процесса, часто повторяющиеся функции покажут реальные горячие места приложения.
```
